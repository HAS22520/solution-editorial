# 常见退化与修法

按出现频率排序。写完题解先扫一遍这张表。

## 1. 复述题目

**症状**：题意段写成 5~10 行，出现"小明""第一行输入""样例解释"。

**修法**：只保留三个成分——输入对象、约束、要求的目标。故事背景、样例、"数据范围"小节全部删掉。目标 ≤ 3 行。

## 2. 代码里塞注释

**症状**：`// 快读`、`# 单调队列维护下标`、`/* 边界处理 */`。

**修法**：全删。注释想表达的因果，本来就是"思路"段该写的东西。删完如果觉得代码看不懂，说明变量名不对——回去改名字，不要加注释。

## 3. 只给步骤，不给理由

**症状**："用单调队列维护，每次弹队尾、弹队首、输出队首。"

**修法**：每个操作后面补一句"为什么合法"。判据：读者能否用这句话反驳你。不能反驳的句子才有信息量。

## 4. C 代码里混进 C++

**症状**：`#include <bits/stdc++.h>`、`bool`、`//`、`vector`、引用参数。

**修法**：按 `references/style-c.md` 的隔离检查表逐条换；用 `gcc -std=c11 -O2 -Wall` 真编译一次。

## 5. Python 直译 Java/C++

**症状**：`class Solution:`、`while i < n` 手写下标、`for (int i...)` 思维、字符串循环拼接。

**修法**：改成 `for i in range(n)`、`deque`、`"".join()`；去掉类壳子。

## 6. 三段代码不等价

**症状**：C++ 用 `deque` 但边界写 `q.front() <= i - k`，C 手写队列写成 `q[head] < i - k`，结果差一。

**修法**：三段共用同一套下标约定（统一 1-based 或统一 0-based），写完拿同一组输入各跑一次，比对输出。

## 7. 复杂度缺失或含糊

**症状**："时间复杂度 O(n) 左右"、"效率较高"、只写时间不写空间。

**修法**：固定写成两句：`时间 O(·)：<一句话理由>`、`空间 O(·)：<一句话理由>`。

## 8. 变量名照抄题目

**症状**：`nums`、`target`、`matrix`、`intervals`、`result`。

**修法**：换成短名表（`n a k ans`）。照抄题目的名字会让代码看起来像 LeetCode 提交记录，不像一份解法。

## 9. 边界只在文字里提，代码里没处理

**症状**：思路写"注意 k 可能大于 n"，代码里没有对应分支。

**修法**：要么在代码里体现，要么在思路里说明"题目保证 k ≤ n"，二选一，不能含糊。

## 附：交付前的三分钟自检

1. 把代码块全删掉，读一遍正文——算法还成立吗？
2. 把正文全删掉，只看代码——能编译、能跑、输出对吗？
3. 三份代码各跑一组含边界的输入（空、1 个元素、极值、全相同）——输出一致吗？
